# Platform skill: auth

Sign-in with an email code, Google or GitHub, through loginbase, with the web cookie layer loginbase lacks and the Google flow loginbase does not have.

## Decision

- loginbase 3.x (npm `loginbase`, HarlonWang) mounted as a Hono sub-app at `/auth`: email OTP (6 digits, 10 minutes), the GitHub OAuth plugin, a 15 minute access JWT, a 30 day rotating refresh token with reuse detection, its own D1 tables and KV counters. The wire protocol is loginbase's `docs/protocol.md`; the product never re-implements it.
- The web layer, added by this skill (`src/server/auth/web.ts`): `/auth/web/*` routes call loginbase in-process. The refresh token lives in an HttpOnly, Secure, SameSite=Lax cookie scoped to `/auth/web`. The access JWT lives in page memory only (`src/lib/auth-client.ts`), never in localStorage, sessionStorage or a readable cookie. Refresh is single-flight.
- `requireUser()` middleware (`src/server/auth/require-user.ts`) turns the Bearer JWT into the `users` row on `c.get("user")`. Every `/api/*` route is behind it unless the route carries an `@public` marker comment.
- `verifiedUser` in `login.ts` (loginbase's `onVerified`, and the Google `done` route) is the only place that creates a `users` row (`findOrCreateUser`). A verified email links to the user who already has it, whatever the provider (Vinci's decision): an email-code user who later chooses Google with the same verified address signs into the same account.
- Google sign-in (version 3), because loginbase 3.1 knows only `email` and `github` and has no provider plugin API: `src/server/auth/google.ts` adds `GET /auth/web/google/start` and `GET /auth/web/google/done`. It is the OpenID Connect authorization code flow with PKCE (S256), a `state` value and a `nonce` in a short-lived (10 minute) `__Host-` HttpOnly, Secure, SameSite=Lax cookie, the code exchanged on the server, and the ID token verified with `jose` (`jwtVerify` against Google's JWKS at `https://www.googleapis.com/oauth2/v3/certs`: the RS256 signature, `iss` = `https://accounts.google.com` or `accounts.google.com`, `aud` = the client id, `exp`, the flow's `nonce`), with `email_verified` required. Then the same user lookup as an email code (`verifiedUser`), loginbase's exported `createSession` and `signAccessToken`, and the same session cookie the GitHub `done` route sets (`setSessionCookie` from `web.ts`, shared, not copied). No other new dependency: `jose` is loginbase's own dependency, pinned at `6.2.13`. The Google files live in `additions/` (factory-written, not yet proven in a kit run), because `reference/` holds only kit files and the kit sync rewrites it; the two changes they need in the kit files are written in the recipe.
- Email transport: the email skill. Until it is selected, loginbase's `email.send` uses the dev transport that writes the code to the log.
- Rate limits: loginbase's KV counters per email and per IP, plus the Workers Rate Limiting binding `AUTH_RATE_LIMITER` (10 a minute per IP) on the code endpoints.
- Fixed screens for the design stage (frontmatter `screens:`): `sign-in` (enter the email, with the "Continue with Google" and "Continue with GitHub" buttons under it, each hidden when its provider is not configured: default, sign-up, error, loading; the `sign-up` state is the same page reached from the nav's Sign up link with the heading and copy of creating an account, because loginbase creates the account on the first verified code and has no separate sign-up), `code` (enter the 6 digits: default, wrong-code, expired, too-many-attempts, loading), `signed-in` (the app shell with the account control), `signed-out` (the app shell after sign out). The design names the rows exactly `Sign in`, `Code`, `Signed in`, `Signed out`.

## Contract

- `POST /auth/web/code/send { email }` answers 200 `{ cooldownSeconds }`, 400 `invalid_email`, 429 `too_many_requests`.
- `POST /auth/web/code/verify { email, code }` answers 200 `{ accessToken, expiresIn, isNewUser, user }` and sets the session cookie; errors pass through from loginbase (`invalid_code`, `code_expired`, `too_many_attempts`).
- `POST /auth/web/refresh` with the cookie answers 200 `{ accessToken, expiresIn }` and rotates the cookie; with no cookie it answers 204 (signed out is normal, not an error).
- `POST /auth/web/logout` revokes the session and clears the cookie, 204. `POST /auth/web/logout-all` (version 2, added by the app-shell skill's account page) calls loginbase's `DELETE /auth/sessions/all` in-process, revokes every session of the user and clears the cookie, 204.
- `GET /api/me/sessions` (version 2) answers `{ sessions: [{ id, createdAt, lastUsedAt, userAgent, current }] }` from loginbase's `sessions` table, read only, for the signed-in user.
- `GET /auth/web/github/start` redirects to loginbase's GitHub start; `GET /auth/web/github/done?otc=` exchanges the one-time code and sets the cookie.
- `GET /auth/web/google/start?next=<path>` (version 3) sets the flow cookie and redirects 302 to `https://accounts.google.com/o/oauth2/v2/auth` with `client_id`, `redirect_uri` = `https://<origin>/auth/web/google/done`, `response_type=code`, `scope=openid email`, `state`, `nonce`, `code_challenge` (S256) and `prompt=select_account`; 404 `not_configured` without the Google secrets. `GET /auth/web/google/done?code=&state=` clears the flow cookie, exchanges the code with the PKCE verifier on the server, verifies the ID token, sets the session cookie and redirects 302 to `next` (default `/app`, same-site paths only). Every failure redirects to `/sign-in?provider=google&error=<code>` with `invalid_state`, `access_denied`, `oauth_failed`, `oauth_no_email` or `not_configured`, and sets no session.
- `requireUser()` sets `c.get("user")` (the `User` from `src/db/users.ts`) and `c.get("sessionId")`; without a valid Bearer it throws 401 `unauthorized` or `invalid_token`.
- In the browser: `apiFetch(path, init)` adds the Bearer token, retries once after a forced refresh on 401, and throws `ApiClientError(status, code, message, fields)`. `loadSession()` resolves `{ status: "signed-in", user } | { status: "signed-out" }` once per page. `signInUrl(next)` is `/sign-in?next=<path>`.
- Cookie name `<product>_session`, path `/auth/web`, `HttpOnly; Secure; SameSite=Lax; Max-Age=2592000`.
- Error envelope on every route: `{ "error": "<code>", "message": "<sentence>", ...fields }`.

## Platform FRs

- **FR-AUTH-1 Request a code.** Given a visitor on the sign-in screen, when they submit a valid email, then a 6 digit code is sent to that address and the code screen shows the address and the cooldown; an invalid email shows the error state and nothing is sent.
- **FR-AUTH-2 Verify the code.** Given a code was sent, when the visitor enters the right code within 10 minutes, then they are signed in (session cookie set, access token in memory) and land on `next`; a wrong code shows the wrong-code state, an expired code the expired state, and the fifth wrong code the too-many-attempts state with a way to request a new code.
- **FR-AUTH-3 Stay signed in and sign out.** Given a signed-in user, when they open a new page, then the session is restored from the cookie without a new code; when they choose Sign out, then the session is revoked on the server, the cookie is cleared and the shell shows the signed-out state; when they choose Sign out everywhere on the account page, then every session of the user is revoked.
- **FR-AUTH-4 Protected API.** Given any `/api/*` route without an `@public` marker, when a request arrives without a valid Bearer token, then the answer is 401 with the error envelope and no data.
- **FR-AUTH-5 GitHub sign-in.** Given the GitHub OAuth app is configured for the env, when the visitor chooses Continue with GitHub and GitHub returns a verified email, then they are signed in like FR-AUTH-2; when it is not configured, the button is not shown.
- **FR-AUTH-6 Google sign-in.** Given the Google OAuth client is configured for the env, when the visitor chooses Continue with Google and Google returns an ID token that verifies (signature, issuer, audience, expiry, nonce) with a verified email, then they are signed in like FR-AUTH-2, into the existing user when that email already has one; when the token does not verify or the email is not verified, the sign-in screen shows the error state and no session is made; when it is not configured, the button is not shown.

## Pitfalls

- Copy loginbase's three migrations and eventbase's migrations, and pass `stats: { db: env.DB }`, because loginbase 3.x writes its login statistics to eventbase's `events` table and no longer writes `auth_events` itself; keep `auth_events` for the raw funnel through `onEvent`.
- Give every test its own email and its own `CF-Connecting-IP`, because the KV cooldown and per-IP counters carry across tests in one file and the second `code/send` otherwise answers 429.
- Test "reuse is revoked" by using the successor token first and then replaying the old one, because the rotation rescues a replayed token once when its successor was never used.
- Call loginbase in-process from the web layer: build a `Request` for `${origin}/auth/<path>` with `Content-Type: application/json`, `X-Client-Platform: web`, the caller's `CF-Connecting-IP` and `User-Agent`, and pass it to `login.fetch(request, env, ctx)`; pass error bodies through unchanged, because the protocol is loginbase's and a re-implementation drifts.
- Put the app's own `https://<origin>/auth/web/github/done` in `allowedRedirects` and the exact registered `https://<origin>/auth/oauth/github/callback` in `callbackUrl`, because GitHub and loginbase both compare them exactly. The `done` route exchanges the one-time code on the server, so the access token never enters a URL.
- Answer `POST /auth/web/refresh` without a cookie with 204, not 401, because a signed-out visitor refreshing on page load is normal and Chromium logs every failed fetch as a console error.
- Set `Secure` on the cookie even for `http://127.0.0.1`, because Chromium and Firefox treat loopback as a secure context and Playwright against wrangler dev works.
- Require a same-origin `Origin` header on every state-changing `/auth/web/*` request, because the cookie routes are the CSRF surface and a browser always sends the header on a fetch POST.
- Use one GitHub OAuth app per env, because an app takes one callback URL and the preview env otherwise answers 404 `not_configured`.
- A new `JWT_SECRET` signs every user out; generate it once per env and keep it outside the repo.
- Show Sign up and Sign in as two nav links to the same `/sign-in` page (`?intent=signup` sets the sign-up state), because loginbase has no separate sign-up and a visitor still looks for the word.
- Islands with controlled inputs set `data-ready="true"` from a `useEffect`, and tests wait for it before `fill`, because Playwright can type before React hydrates and the submit then sends an empty value.
- Verify the Google ID token with `jwtVerify` and Google's JWKS, never only decode it (`decodeJwt`, `atob` on the middle part), because an unverified token is a sign-in as anyone; the check refuses a Google route that decodes without the verify call.
- Check the `nonce` of the flow and `email_verified`, because a valid token replayed from another flow, or a Google account with an unverified address, would otherwise sign into the user who owns that address.
- Keep the Google flow cookie SameSite=Lax, not Strict, because Google returns with a top-level GET from accounts.google.com and a Strict cookie is not sent on it; give it the `__Host-` prefix (Secure, `Path=/`, no Domain), because a sibling Worker on the same `*.workers.dev` account could otherwise set it.
- Register the redirect URI exactly (`https://<origin>/auth/web/google/done`, no trailing slash) in each env's Google OAuth client, because Google compares it byte for byte and answers `redirect_uri_mismatch`; one client per env, like GitHub.
- Keep the Google access token out of every URL: the `done` route sets the session cookie and redirects, and the page gets its access token from `POST /auth/web/refresh`, as after GitHub.
